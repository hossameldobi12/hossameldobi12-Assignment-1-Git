# Git Notes

## git squash

**يعني إيه؟** عندي Feature معينة وعملت فيها أكتر من Commit، فبدل ما الـ History يبقى فيه كل الـ Commits دي، أقدر أجمعهم في Commit واحدة.

**بيستخدم إمتى؟** قبل ما أعمل Merge أو Pull Request، لو عندي أكتر من Commit لنفس الـ Feature وعايز أخلي الـ History أنضف.

**مثال عملي:** بعمل Update لـ Feature معينة، وكل شوية بعمل Commit لتعديل صغير أو إصلاح Bug. في الآخر، بدل ما تظهر كل التعديلات الصغيرة بشكل منفصل، بخليهم Commit واحدة بتوضح إنّي خلصت الـ Feature.

---

## git merge vs git rebase

**يعني إيه؟**

- **Merge:** بيدمج التغييرات الموجودة في Branch مع Branch تاني، وبيحافظ على تاريخ الـ Commits زي ما حصل.
- **Rebase:** بينقل الـ Commits بتاعتي بحيث تبدأ من آخر تحديثات الـ Branch التاني، وده بيغيّر شكل الـ History.

**بيستخدم إمتى؟** بستخدم Merge لما أكون عايز أجمع التغييرات مع الاحتفاظ بتاريخ الفروع، وبستخدم Rebase لما أكون عايز أخلي الـ History خطّي ومنظم.

**مثال عملي:** أنا شغال على Feature، وفي نفس الوقت فيه تحديثات جديدة نزلت على `main`. باستخدام Merge، بدمج التحديثات مع شغلي، أما باستخدام Rebase، بخلي شغلي يبدأ من آخر تحديثات `main` كأنّي بدأت بعديها.

## git help

**يعني إيه؟** بيساعدني أعرف طريقة استخدام أوامر Git والـ Options المتاحة لكل أمر.

**بيستخدم إمتى؟** لما أنسى طريقة استخدام Command معينة أو أحتاج أعرف تفاصيل أكتر عنها.

**مثال عملي:** لو محتاج أستخدم أمر معين ومش فاكر الـ Options بتاعته، أقدر أراجع المساعدة الخاصة بيه وأعرف كل Option بتعمل إيه قبل ما أستخدمه.

---

## git clean

**يعني إيه؟** بيحذف الملفات اللي Git مش بيتابعها، واللي اسمها **Untracked Files**.

**بيستخدم إمتى؟** لما يكون عندي ملفات مؤقتة أو ملفات تجربة مش محتاجها، وعايز أنضف الـ Working Directory.

**مثال عملي:** أثناء تطوير Feature، عملت شوية ملفات للتجربة وبعد ما خلصت اكتشفت إنك مش محتاجها. تقدر تستخدم Git Clean عشان تتخلص من الملفات دي بدل ما تفضل موجودة في المشروع.

**خلي بالك:** الملفات دي ممكن تتحذف نهائيًا، فالأفضل تتأكد من الملفات اللي هتتحذف قبل التنفيذ.

---

## git shortlog

**يعني إيه؟** بيعرض ملخص لمساهمات الـ Contributors في المشروع، زي عدد الـ Commits الخاصة بكل شخص.

**بيستخدم إمتى؟** لما أكون عايز أعرف مين ساهم في المشروع وأشوف ملخص سريع لتوزيع الـ Commits.

**مثال عملي:** عندك Project بيشتغل عليه أكتر من Developer، وعايز تعرف كل واحد عمل كام Commit. تقدر تستخدم Git Shortlog عشان تعرض ملخص المساهمات دي.

---

## git cherry-pick

**يعني إيه؟** بيسمحلي آخد Commit معينة من Branch وأطبق التغييرات بتاعتها على الـ Branch الحالي، من غير ما أدمج كل التغييرات الموجودة في الـ Branch التاني.

**بيستخدم إمتى؟** لما أحتاج تغيير معين موجود في Branch تاني، لكن مش محتاج باقي التغييرات الموجودة فيه.

**مثال عملي:** زميلك عمل Fix لـ Bug في Branch خاص بيه، لكن الـ Branch فيه Features تانية لسه مش جاهزة. بدل ما أدمج الـ Branch كله، أقدر أنقل الـ Commit الخاصة بالـ Fix بس.

---

## git bisect

**يعني إيه؟** بيساعدني أعرف أنهي Commit سببت ظهور Bug باستخدام **Binary Search**، بدل ما أراجع كل الـ Commits واحدة واحدة.

**بيستخدم إمتى؟** لما يكون المشروع كان شغال بشكل سليم، وبعد مجموعة من التعديلات ظهر Bug ومش عارف سببه أنهي تعديل.

**مثال عملي:** عندك 100 Commit، والمشروع كان شغال قبل التعديلات دي، لكن دلوقتي فيه Bug. بدل ما تراجع الـ 100 Commit يدويًا، Git بيساعدك تختبر نسخ مختلفة لحد ما تحدد الـ Commit اللي دخلت المشكلة.

---

## git prune

**يعني إيه؟** بيحذف بعض الـ Git Objects اللي بقت غير قابلة للوصول من الـ References الموجودة في المستودع.

**بيستخدم إمتى؟** في عمليات صيانة الـ Repository وتنظيف الـ Objects القديمة اللي مبقاش فيه حاجة بتوصل ليها.

**مثال عملي:** بعد عمليات معقدة لتعديل الـ History، ممكن تفضل Objects قديمة مش مرتبطة بأي Branch أو Reference. Git Prune ممكن ينضف الـ Objects دي لما تكون مؤهلة للحذف.

**خلي بالك:** مش أمر محتاج تستخدمه بشكل يومي، لأن Git عنده آليات تنظيف تلقائية، والحذف ممكن يأثر على إمكانية استرجاع بيانات قديمة.

---

## git worktree

**يعني إيه؟** بيسمحلي أشتغل على أكتر من Branch في نفس الوقت، وكل Branch يكون موجود في Working Directory منفصل.

**بيستخدم إمتى؟** لما أكون شغال على Feature، وفجأة أحتاج أعمل Fix سريع في Branch تاني من غير ما أوقف شغلي الحالي.

**مثال عملي:** أنا شغال على Feature في مجلد المشروع الأساسي، وفجأة ظهر Bug محتاج يتصلح على `main`. بدل ما أغيّر الـ Branch وأأثر على الملفات اللي شغال عليها، بقدر أشتغل على `main` من مجلد منفصل وأسيب الـ Feature زي ما هي.

---

## git verify-commit

**يعني إيه؟** بيتحقق من الـ Digital Signature المرتبطة بالـ Commit، لو كانت موقعة.

**بيستخدم إمتى؟** لما يكون المشروع محتاج يتأكد من توقيعات الـ Commits، خصوصًا في المشاريع اللي بتشترط إن التعديلات تكون موقعة.

**مثال عملي:** لو الفريق عنده سياسة بتشترط توقيع الـ Commits، تقدر تتحقق من توقيع Commit معينة وتتأكد إن التوقيع صالح بناءً على إعدادات الثقة الموجودة عندك.

---

## git filter-repo

**يعني إيه؟** أداة خارجية بتساعدني أعمل Filter أو Rewrite للـ Git History، زي إزالة ملفات أو مجلدات من تاريخ المشروع.

**بيستخدم إمتى؟** لما أحتاج أعدل تاريخ المشروع بالكامل، مثل إزالة ملف حساس من الـ History أو فصل مجلد معين من Repository كبير.

**مثال عملي:** اكتشفت إن ملف فيه بيانات سرية اتضاف للمشروع من فترة، وبعدها اتعملت Commits كتير. حذف الملف في Commit جديدة مش كفاية، لأن محتواه ممكن يفضل موجود في الـ History القديمة. الأداة دي بتساعدك تعيد كتابة التاريخ لإزالة الملف من الـ Commits السابقة.

**خلي بالك:** إعادة كتابة الـ History بتغيّر الـ Commit IDs، وممكن تحتاج تنسيق مع الفريق. ولو البيانات السرية اتنشرت، لازم تلغيها أو تغيّرها، لأن حذفها من الـ History وحده مش كفاية.

## git grep

**يعني إيه؟** بيساعدني أبحث عن نص أو Pattern داخل الملفات اللي Git بيتابعها في المشروع.

**بيستخدم إمتى؟** لما أحتاج أعرف مكان استخدام Method أو Variable أو نص معين، خصوصًا في المشاريع الكبيرة.

**مثال عملي:** عندك ASP.NET Core Project وفيه Method اسمها `CalculateTotal`، ومش فاكر كل الأماكن اللي بتستخدمها. تقدر تبحث عن الاسم وتشوف الملفات والأسطر اللي ظهر فيها بدل ما تفتح كل ملف يدويًا.

---

## git blame

**يعني إيه؟** بيوضح مين آخر شخص غيّر كل سطر في ملف معين، والـ Commit اللي حصل فيها التغيير.

**بيستخدم إمتى؟** لما أراجع كود موجود وأحتاج أفهم سبب كتابة سطر بطريقة معينة أو أعرف تاريخ التعديل.

**مثال عملي:** بتراجع Method في مشروعك ولقيت Condition مش واضحة. تقدر تعرف مين آخر شخص عدّل السطر، وبعدها تراجع الـ Commit المرتبطة بيه عشان تفهم سياق التغيير.

**خلي بالك:** Git Blame بيوضح آخر شخص غيّر السطر، لكن ده مش معناه إنه الشخص الوحيد المسؤول عنه أو إنه سبب المشكلة بالضرورة.
